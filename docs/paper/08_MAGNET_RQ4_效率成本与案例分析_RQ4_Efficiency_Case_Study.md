# MAGNET 实验规划与结果初稿：RQ4（效率、成本与案例分析）

> 本文档基于 `result/007swe_clean15_agent_Qwen3.5-397B-A17B_swe_clean15_max_quality_r5` 的 92 个完整样本。当前数字可用于 MAGNET 内部效率分析；在未获得同模型、同样本、同计价口径的 baseline 日志前，不对不同论文中的美元成本作直接优劣声称。

## RQ4：MAGNET 具有怎样的计算成本与搜索行为？

RQ4 拟回答两个互补问题：

1. MAGNET 完成一个多模态仓库级定位任务需要多少时间、LLM 请求和 token，成本主要产生于哪些阶段？
2. 动态搜索何时能以较少轮次收敛，何时会陷入冗余扩展，这些行为如何影响单目标与多目标定位？

这一组织方式结合了三类已有实验惯例。LocAgent 同时报告平均交互轮数、平均成本和 Acc@10/Cost；CoSIL 联合报告 token、成本与定位性能，并通过搜索轨迹解释冗余扩展；GraphLocator 将图构建时间与 LLM 交互成本分开，并按 symptom-to-cause 距离和 gold 函数数量分析难度。MAGNET 依此报告“端到端开销、阶段开销、收敛行为和失败边界”，而不把一个单一成本数字解释为效率的全部。

## 4.1 统计口径与成本审计

### 时间与交互

对样本 \(i\)，端到端时间 \(t_i\) 从样本进入 `run_localization_pipeline` 前开始计时，在定位、评价与结果序列化完成后停止。阶段时间只累加不重叠的顶层阶段，不直接求和嵌套的 `dynamic.*` 子阶段，否则会双重计时。交互数指返回成功 API 响应的 LLM 请求数，不将工具函数内部的非 LLM 操作计为模型交互。

### Token 与费用

对样本 \(i\) 的第 \(j\) 次成功请求，从 API 响应 `usage` 中读取输入 token \(T_{ij}^{\mathrm{in}}\) 和输出 token \(T_{ij}^{\mathrm{out}}\)，样本级 token 为

$$
T_i^{\mathrm{in}}=\sum_j T_{ij}^{\mathrm{in}},\qquad
T_i^{\mathrm{out}}=\sum_j T_{ij}^{\mathrm{out}},\qquad
T_i=T_i^{\mathrm{in}}+T_i^{\mathrm{out}}.
$$

若服务商对每百万输入和输出 token 的价格分别为 \(p_{\mathrm{in}}\) 和 \(p_{\mathrm{out}}\)，则

$$
C_i=\frac{T_i^{\mathrm{in}}}{10^6}p_{\mathrm{in}}
+\frac{T_i^{\mathrm{out}}}{10^6}p_{\mathrm{out}}.
$$

当前代码与 `.env.local` 没有记录 Qwen3.5-397B-A17B 所用私有 API 的合同价格，因此暂不填写虚构的美元或人民币费用。本次完整运行的可计价表达式为

$$
C_{\mathrm{run}}=11.279754p_{\mathrm{in}}+1.841172p_{\mathrm{out}},
$$

平均每例为

$$
\overline{C}=0.122606p_{\mathrm{in}}+0.020013p_{\mathrm{out}}.
$$

只要将费率的货币单位统一为“每百万 token”，即可直接得到整体与单例费用。若服务商额外按图像数量、图像分辨率或缓存命中计费，这部分需根据账单单独补充，不应从文本 token 反推。

### Token 口径的必要修正

当前 `collect_token_usage` 递归遍历结果中的 `usage` 和 `token_usage`，并且只依赖 Python 对象身份去重。同一次 LLM 请求的 usage 若被复制到多个轨迹字典，序列化后会被重复累加。这次运行中：

- `per_instance_metrics.csv` / `token_usage.jsonl` 的递归汇总为 **14,433,034 token**；
- `run.log` 中 3,381 条 `[llm:ok]` 成功响应的 usage 之和为 **13,120,926 token**；
- 前者比请求级口径高 **10.0%**。

因此，本 RQ 使用 `run.log` 的请求级 usage 作为主口径，现有 CSV token 仅用于定位记录问题。后续应为每次响应持久化唯一 `request_id` 并按 ID 汇总，不应用文本哈希去重，因为两次合法请求可能恰好包含相同内容。

顺序执行 92 个样本共需要约 **9.33 小时**，平均每例约 **6.08 分钟**。LLM 请求累计时间占端到端时间的约 **70.0%**，说明服务端推理与网络等待是主要延迟来源。需要注意，“源码读取计数”可包含跨轮重复读取，不等于唯一文件数。

成本分布存在明显长尾。`chartjs__Chart.js-8650` 包含 73 个图像引用，该样本共产生 110 次成功 LLM 请求、487,871 token 和 849.25 秒端到端时间，均为本次运行最高值。按图像数量分组时，1 张图像的 48 例平均消耗 135,160 token，2–5 张图像的 37 例为 135,442 token，而至少 6 张图像的 7 例上升到 231,698 token。由于最后一组样本很少且任务难度不受控，该结果只用于识别多图像预算上限和证据去重需求，不作因果解释。

动态定位占据 **75.9%** 的时间和 **77.7%** 的 token。其中，每轮候选审查和控制决策合计占总 token 的 **69.9%**，是最优先的优化对象。因此，下一版的效率优化不应首先压缩已经很快的结构索引，而应减少无新证据轮次中的全量候选重审，并将审查限定为新增、排名变化或尚未落地的候选。

### 动态停止是否减少开销

<p align="center"><strong>表 3. 提前收敛样本与达到 14 轮上限样本的描述性对比。</strong></p>

| 组别 | N | 时间（s/例） | Token/例 | LLM 请求/例 | File Acc@1 | File Acc@15 | File Recall@15 | File SL@15 | 修改集 F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 提前收敛（<14 轮） | 43 | 249.8 | 93,433 | 26.4 | 51.2% | 90.7% | 71.2% | 55.8% | 29.8% |
| 达到上限（14 轮） | 49 | 466.1 | 185,781 | 45.8 | 26.5% | 81.6% | 58.2% | 42.9% | 14.7% |

43/92（**46.7%**）的样本在 14 轮之前停止。与达到轮数上限的样本相比，这一组的平均时间低 46.4%，token 低 49.7%，同时定位指标更高。这一结果说明系统确实为部分容易样本分配了较少预算，但不能解释为“提前停止导致了更高准确率”，因为难例本身更容易运行到上限。这里是内生分组，不是随机对照实验。

全部样本上，token 与 File Acc@1、File Recall@15 的 Spearman 相关分别为 -0.247 和 -0.126，时间与 File Recall@15 的相关为 -0.401。这些值不证明增加预算会降低准确率，但表明在当前控制策略下，高开销通常是未收敛和难例的结果，而非更多有效证据的保证。因此，效率优化应面向“新证据增益”，而不是简单追求更少轮数。

ReAct 工具 Agent 的停止原因分布为：`evidence_plateau_after_tool_coverage` 43 例，`max_steps_reached` 42 例，`duplicate_tool_action_without_evidence_gain` 7 例。近一半样本仍以步数上限结束，说明当前的证据平台检测仍有较大改进空间。

### 多目标难度是主要失败边界

| Gold 文件数 | N | 时间（s/例） | Token/例 | File Acc@15 | File Recall@15 | File SL@15 | 修改集 F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 33 | 335.3 | 137,895 | 84.8% | 84.8% | 84.8% | 30.3% |
| 2 | 21 | 331.3 | 128,560 | 85.7% | 71.4% | 57.1% | 22.5% |

随着 gold 文件数增加，Acc@15 仍稳定在约 85%–88%，但 Recall@15 从 84.8% 降至 34.9%，SL@15 从 84.8% 降至 5.9%。这说明 MAGNET 对复杂样本通常能找到至少一个核心文件，但尚未稳定恢复完整的跨文件职责链。同时，≥6 文件组的平均时间和 token 分别增至 455.4 秒和 17.38 万，额外搜索开销并未转化为相称的完整覆盖。这一边界与 GraphLocator 按 gold 函数数量分组的分析思路一致，但本文按实际评价的 gold 文件数量分组。

## 4.3 典型案例选择与轨迹分析

案例不按主观印象挑选，而是先定义三种行为类型，再在各类中选择具有完整轨迹和明确 gold patch 的样本：

1. **高效完整成功**：Acc@1=1、Recall@15=1、修改集精确命中，且轮数低于上限。
2. **核心命中但职责不完整**：Top-1 正确，但多文件 Recall/SL 较低。
3. **高成本失败**：达到轮数上限且 Acc@15=0，用于分析错误证据和搜索偏移。

<p align="center"><strong>表 5. RQ4 的三个候选案例。</strong></p>

| 案例 | 类型 | Gold 文件 | 轮数 | LLM 请求 | Token | 时间（s） | Acc@1/15 | Recall@15 | 修改集 F1 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `processing__p5.js-3068` | 高效完整成功 | 1 | 3 | 18 | 54,237 | 162.9 | 1 / 1 | 100.0% | 100.0% |
| `Automattic__wp-calypso-21409` | 核心命中、多职责部分覆盖 | 10 | 6 | 25 | 84,505 | 292.7 | 1 / 1 | 60.0% | 16.7% |
| `chartjs__Chart.js-9027` | 高成本完全失败 | 1 | 14 | 46 | 194,110 | 326.5 | 0 / 0 | 0.0% | 0.0% |

### 案例 A：显式符号与预期效果引导快速收敛

`processing__p5.js-3068` 报告 `loadStrings()` 丢弃空行，导致 shader 错误的源码行号错位。Gold patch 仅修改 `src/io/files.js`，将过滤非空行的正则匹配改为保留空行的换行分割。MAGNET 将 `loadStrings`、`empty_lines` 和“保留行号”组织为符号、状态与效果证据，在 3 轮内将 `src/io/files.js` 排在 Top-1，最终修改集也只包含该文件。该案例说明，当 issue 中存在可落地的 API 名和明确行为不变量时，外部演示 URL 即使不能访问，本地源码搜索仍可快速收敛。

不过，该样本的 `closure_status` 仍为 `incomplete`，因为审查器未标记 `root_patch_mechanism` 已验证，而评价上的修改集恰好完全正确。这是一个需要报告的内部状态校准问题：“证据完整”与“预测正确”不能混为同一指标。

### 案例 B：URL 种子能帮助找到核心位置，但不足以恢复完整职责链

`Automattic__wp-calypso-21409` 要求在 WooCommerce 商店注册流中，针对非支持国家的用户强制验证邮箱。Issue 给出了 `isCurrentUserEmailVerified` selector URL，但 gold patch 横跨 dashboard 流程、地址表单、国家数据、state action 等 10 个文件。MAGNET 将 selector 视为低修改先验的导航种子，并将实际流程文件 `store-location-setup-view.js` 排到 Top-1，这一过程体现了从证据位置到实现位置的纵向导航。

然而，Top-15 只覆盖 6/10 个 gold 文件，最终修改集只有 2 个文件，其中 1 个为 gold。系统在重复工具动作无新证据后停止，但仍缺失根修改机制的验证。该案例表明，“找到一个核心 UI 文件”不等于“找全一次跨层功能修改”。后续需将未覆盖的职责显式分解为流程控制、交互组件、状态读取、action 更新与跳转目标，而不是只用通用 concern 词扩展文件。

### 案例 C：堆栈符号丢失和泛化流义务导致高成本偏移

`chartjs__Chart.js-9027` 的表面异常是 `Intl.NumberFormat` 收到 `NaN` 的 `minimumFractionDigits`，但 issue 同时指出 chart height 被计算为 `NaN`，堆栈中包含 `fitBoxes`。Gold patch 位于 `src/core/core.layouts.js`，通过将可用宽高限制为非负数修复布局源头。这是典型的 symptom-to-cause 距离：异常抛出位置在格式化帮助函数，真正修改位置却在上游布局计算。

当前轨迹暴露了四个具体问题。首先，`_extract_entities` 在常规标识符抽取前删除 fenced code，因而堆栈中的 `fitBoxes` 没有进入高优先级显式实体，只作为普通 concern 保留。其次，由视觉和 LLM 结果产生的“navigation/link target”、“legend interaction”等泛化语义进一步触发 URL、UI event 和 style 流义务，将搜索引向 `plugin.legend.js`、`plugin.tooltip.js` 和 `plugin.filler.js`。再次，三张图像生成的同类 visual hypotheses 在 `hypotheses` 中重复三次，说明字符串列表去重没有扩展到结构化假设。最后，尽管系统执行了 72 次源码读取记录和 56 条流轨迹，候选审查仍未验证修改机制，却没有触发“回到堆栈显式符号并向上游追溯”的定向回退。

这一案例的优化顺序很明确：先增加堆栈专用解析并保留函数符号；再要求流义务由原始 issue 证据触发，不得由泛化的生成 effect 二次触发；然后对结构化 visual hypotheses 按 `(source, value, role)` 去重；最后在多轮未验证机制时，强制执行显式符号反向依赖回退，而不继续扩展通用 UI 候选。

## 4.4 论文正文的建议呈现

RQ4 正文建议只保留一张表和一张图：

1. **效率主表**：报告平均/中位时间、输入/输出 token、请求数、轮数和实际费用。若取得 baseline 同口径日志，在同表中加入 LocAgent、CoSIL 和 GraphLocator；否则只报 MAGNET，不复制跨论文不可比的成本。
2. **组合图**：(a) 证据理解、索引和动态定位的时间占比；(b) 证据理解、控制器、候选审查和工具 Agent 的 token 占比；(c) 三个案例的简化搜索轨迹。

正文用两段回答问题：第一段说明总体开销与主要瓶颈，第二段说明提前收敛能节省预算，但多文件职责恢复和失败轮次仍是主要边界。完整分位数、停止原因、任务类型、图像数量、每样本 token 和轨迹表放入附录或复现材料。

**RQ4 回答初稿。** MAGNET 在 SWE Clean15 上平均每例消耗 365.02 秒、36.75 次成功 LLM 请求和 142,619 token。动态定位是主要开销来源，而候选审查与控制决策合计占总 token 的 69.9%。约 46.7% 的样本能在轮数上限前收敛，其成本约为达到上限样本的一半。然而，当真实修改文件达到 6 个以上时，Recall@15 和 SL@15 分别降至 34.9% 和 5.9%，表明多职责恢复而非单一核心位置命中，是当前性能与效率的共同瓶颈。

## 4.5 投稿前的执行清单

| 优先级 | 工作 | 目的 | 是否需要重跑 92 例 |
| --- | --- | --- | --- |
| P0 | 用 `[llm:ok]` 生成请求级 token ledger，并按唯一 request ID 修复后续汇总 | 消除 10.0% 重复计数 | 否，当前运行可从日志重建 |
| P0 | 从 API 账单或官方合同获得 \(p_{\mathrm{in}},p_{\mathrm{out}}\) 及图像计价规则 | 计算真实费用 | 否 |
| P0 | 去除数据中重复的 `[Multimodal Context - Compact]` 块，或在进入 prompt 前去重 | 减少固定输入开销和重复假设 | 新版需要，当前 RQ4 保留原运行口径 |
| P1 | 实现堆栈专用符号抽取、结构化假设去重和原始证据门控的 flow obligation | 避免 Chart.js-9027 类的搜索偏移 | 需要作为新版主结果验证 |
| P1 | 候选审查改为 delta review，连续无机制证据时触发定向回退 | 降低占比 39.4% 的审查 token | 需要作为效率优化实验 |
| P1 | 对三个案例人工核对 issue、gold patch、每轮 Top-5 和强制停止原因 | 保证案例图不将模型推断当作事实 | 否 |
| P2 | 在固定 30–50 例分层子集上，用同一 Qwen3.5 端点复跑 LocAgent、CoSIL 和 GraphLocator | 得到可公平比较的 baseline 时间/token/成本 | 否，可用预注册子集 |

当前 92 例的 `problem_statement` 均包含 3 个 `[Original Issue]` 标记和 3 个 `[Multimodal Context - Compact]` 块，后者确实重复了视觉/网页上下文。这一数据预处理问题会增加输入 token，并在多图像样本中放大重复查询。为保持与 RQ1 同一运行条件，当前 RQ4 应报告真实已发生的成本，不从旧日志中估算“去重后成本”；去重收益应作为后续独立的效率对照实验。
