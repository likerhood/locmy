# MAGNET：定位、效率与下游修复实验规划

核对日期：2026-09-10。本文是实验设计与本地审计，不是已经完成的修复实验结果。推荐主方案：两个数据集各 50 个固定实例、同一定位模型、同一修复模型、统一代码上下文预算，先完成单补丁主实验，再按预算扩展候选补丁数。保留 92/458 例定位主实验。

## 1. 文献依据与截图的正确用法

### LocAgent

核对版本为 [ACL 2025 正式论文](https://aclanthology.org/2025.acl-long.426.pdf)，代码为 [gersteinlab/LocAgent](https://github.com/gersteinlab/LocAgent)。表 5 联合报告交互轮数、费用与函数 Acc@10/Cost；该比值使用准确率小数，而不是直接把百分数除以费用。正文 5.8 固定 Agentless 编辑流程与 Claude-3.5 编辑模型，改变定位方法。表 8 中 Agentless 的 Pass@1/10 为 26.31/33.58，LocAgent-Claude 为 27.92/37.59，LocAgent-Qwen 微调模型为 26.79/36.13。这里的 12% 是 33.58→37.59 的相对提升，绝对提升为 4.01 个百分点。该表的精确采样估计和筛选细节不能仅由截图推断，更不能将 Pass@10 自动理解成提交一个选中补丁的成功率。

### CoSIL

核对版本为 [arXiv v3，Issue Localization via LLM-Driven Iterative Code Graph Searching](https://arxiv.org/html/2503.22424v3)。早期标题是 Software Issue Localization via LLM-Driven Code Repository Graph Searching，属于同一工作的版本差异。

其 IV-E/RQ3 采用 Agentless-1.5 修复与验证，Top-3 定位、10 个候选补丁（1 个 greedy、9 个 temperature=0.8），定位来自 Qwen2.5-Coder-32B；表 VI 中 GPT-4o 指修复模型。Lite 上 CoSIL+Agentless 的 25.67% 对应 Agentless 的 22.33%，差 3.34 个百分点。表 VII 的 50+50 属于跨模型定位/成本子实验；表 VI 使用 Lite 300、Verified 500。表 IX 的 40 候选比较也表明更高定位分数不保证更高最终解决率。因此借鉴其控制变量与指标，不照搬不同规模的绝对成绩。[论文](https://arxiv.org/html/2503.22424v3)

本地 `alltry/code/CoSIL/patch_gen.sh` 提供实际集成入口：函数结果→fine_grain_line_level→repair→regression/reproduction→rerank→harness。但该文件同时出现 `--max_samples 20`、验证索引 0–9、重排 `--num_samples 10`，说明脚本默认值不能视为表 VI 的完整可复现配置。正式实验必须显式冻结每一步参数、候选 ID 与实际使用数量。[官方仓库](https://github.com/ZhonghaoJiang/CoSIL)

### 对本文更关键的启发

我们应拆开三个问题：定位候选是否更好；这些候选交给相同修复器是否更有用；获得同样解决率需要多少端到端资源。图搜索、剪枝、多目标定位本身已经有相关工作，尤其 [GraphLocator](https://arxiv.org/abs/2512.22469) 已讨论 symptom-to-cause 与 one-to-many mismatch。MAGNET 的创新表述应落到多模态证据如何落地到代码、如何触发受限的流验证，以及证据如何在有限预算下转化成可用的修复上下文。

## 3. 50+50 抽样：可以做，但必须界定研究范围

### 主方案

每个数据集按仓库比例分配 50 个名额，使用最大余数法；仓库内按固定 seed 与 instance_id 的 SHA-256 排序。所有方法使用完全相同的实例、base_commit 与输入快照。抽样不读取定位排名、gold 修改数量或修复结果。

本次已生成：`swe_provisional50.csv`、`omni_provisional50.csv`；另有全量 `*_candidate_order.csv` 记录同仓库候补顺序。seed 为 `magnet-downstream-20260910-v1`。这是候选名单，**没有运行环境预检，也没有形成正式冻结测试集**。

SWE 分配：wp-calypso 18、Chart.js 12、p5.js 8、marked 7、react-pdf 5。Omni 分配见审计文件，覆盖 15 仓库；语言为 Python 20、JS 15、TS 11、Java 4。

该次结果中 Omni 50 只有 1 个 `image_urls` 非空实例；如实保留，不能换 seed 直到出现有利样本。推荐将 SWE50 用作视觉任务下游验证、Omni50 用作多语言/网页证据场景迁移验证，不对 Omni50 做图像收益统计。图像机制消融可在全量 Omni34 图像链接样本上只做定位，必要时人工标注图像是否必需。

若研究目标明确要求 Omni 下游图像代表性，应在运行任何修复结果前改用预声明的 repo×image 分层设计（例如图像 4、非图像 46），发布新版本清单，并记录这一估计目标。不要使用“图像 25+文本 25”后仍宣称代表原 458 分布。

### 正式冻结前的环境流程

1. 按候选清单检查实例 ID/version/base_commit 能否与官方数据和镜像匹配。
2. 每例在独立 evaluator 容器运行 no-op 负控与 gold patch 正控；要求负控未解决、正控解决，测试解析正常。
3. 失败要区分镜像/网络/依赖、测试 flaky、数据映射与真正不适用。对基础设施故障允许预设次数的重试。
4. 只有在看任何方法的修复结果之前，才可按同仓库候补顺序替换环境不可复现样本，记录排除原因。候补不足时报告实际样本量或发布新协议，不能默默换仓库。
5. 冻结后不因某方法失败而换样本；同一问题影响全部方法的基础设施故障需统一处理并做缺失敏感性报告。

若已经对 92/458 的定位成绩反复调参，新抽出的 50 不是未见测试集。论文应称“既有基准上的固定下游验证子集”，而不是“独立 holdout”；在下游运行前冻结方法，此后不根据解决率选版本。

### 小样本能说明多大问题

每集合 50 例，多解决 1 例就是 2 个百分点；不能期待稳定复现 1–3 个百分点的文献增益。以假设的 10/50 为例，Wilson 95% 区间约 11.2%–33.0%，仅用于说明不确定性，不是项目结果。

方法间使用逐例配对差值；报告 wins/losses/ties、解决率差与配对 bootstrap 区间，必要时用 exact McNemar 检验。若只有 2 个 ours-only、0 个 baseline-only，双侧 exact p=0.5；6:0 才达到 0.03125，且这不保证其他比较也显著。预先指定 MAGNET vs CoSIL 为主要比较，其余探索性比较注明多重性。两个集合分别报告；汇总的 100 例结果不是自动证明两个集合均有收益。同仓库相关性需承认，5 仓库不足以保证稳定的 cluster bootstrap。

| 诊断，不参与排名 | Gold-location + 同一修复器 | 检查修复器及上下文是否限制收益；不是保证单调更高的数学上界 |

全部标明 `LocAgent (adapted)`、`CoSIL (adapted)` 等本地适配情况。现有 muladapter 支持多语言实体和 CodeV 风格上下文，不能说原版自然支持 JS/TS/Java。冻结 git SHA、补丁 diff、图解析器、模式、prompt 与模型端点。不以服务名称推断底层模型版本或价格。

## 5. 修复实验：建议定义两个不同问题

### 主实验 A：定位结果本身的下游效用

固定一个修复模型、相同编辑 prompt、相同输入证据和相同上下文打包器，只替换定位结果。所有方法输出去重后的 Top-5 文件与可选实体区间；打包器依据 base_commit 源码按固定排序、截断和上下文配额生成输入。先在不属于最终 100 例的少量开发样本完成 JS/TS/Java/Python smoke test。

推荐初始配置（方案参数，不是已调优结果）：Top-5 文件，代码上下文上限 24k token，每文件软配额并允许剩余配额重分配，输出上限 8k，temperature=0，单候选；若模型上下文不支持则在开发阶段统一降低。总输入还需为 issue、图像/统一证据留出固定预算；tokenizer 以同一修复模型计算。

默认修复范围限制在提供的文件；不允许额外仓库搜索，以免修复器重新定位掩盖差异。跨文件补丁允许但必须在候选集合内。若代码打包截断导致目标实体丢失，计入 adapter/context failure，不归咎于定位算法。测试相关修改与资产修改遵循数据集官方规则，不能自定“凡测试文件一律禁改”而排除本来的任务。

选择 Top-5 是针对本地较深召回的预算折中，不是 CoSIL 原表的直接复现。可在预先选好的诊断子集比较 Top-3/5/10；不能看到正式解决率后选最优 k 作为唯一主结果。

主表的所有修复器使用同一份原始 issue 与统一证据包，不额外给 MAGNET 自有推理链。公共证据预处理若被使用，其成本对每种完整系统都计入；同时报告共享资源的边际成本。定位阶段允许的方法工具访问也应一致记录。只有 MAGNET 看图、baseline 只看文本的比较测量的是系统组合差异，不能声称隔离了搜索算法贡献。

### 补充实验 B：MAGNET 证据包是否进一步有用

固定 MAGNET 的定位列表、相同 token 上限和修复模型，对比：位置+源码；位置+源码+MAGNET 证据摘要。摘要不含 gold、标准补丁或未来 PR。将摘要占用的 token 从总输入预算扣除，记录源码截断差异。这个比较回答 evidence-aware repair，而不是把证据收益混入主定位表。

`final_patch_set` 只用于附加诊断，比较它与 Top-5 的代码覆盖和解决数。只有确认它具有稳定收益后，才考虑作为论文默认修复接口。

## 6. 指标与候选补丁协议

主结果为 `Resolved-single = 100 × solved(selected single patch)/50`，由对应官方测试 harness 判定；不是由 LLM 判正确，也不是与 gold diff 字符串相同。

同时记录：

| 指标 | 明确定义 |
|---|---|
| Nonempty patch % | 产生非空补丁的实例比例 |
| Applied % | 所选非空补丁能由冻结的应用程序成功应用到 base_commit 的比例，分母 50 |
| Syntax/build pass % | 若能统一实现则单列；不能将 git apply 成功等同语法正确 |
| Resolved % | 通过官方解决判定的比例，分母 50 |
| Failure categories | 空定位、上下文无效、空补丁、应用失败、测试不通过、超时、基础设施失败 |
| End-to-end cost | 定位、公共证据、源码细化、修复、筛选、评测分项及总和 |

扩展预算时，建议从 K=1 扩到 K=3，再考虑 K=5/10。混合 1 个 greedy+2 个随机候选属于预定搜索协议：报告 `Best-of-3/oracle success`（任一候选通过）和 `Selected@3`（只用允许的开发侧测试/筛选选一个），不要把前者冒充可部署解决率。官方隐藏测试只能最终评价，不可用来选择要提交的补丁。

若要报告标准 pass@k，需固定 n 个同分布随机采样补丁，逐例正确数 c，使用 `1-C(n-c,k)/C(n,k)` 并对实例取均值。greedy 与不同温度混合、只补采失败实例、删除坏格式样本后重采，都不能不加说明地套用该估计。重复补丁仍消耗采样预算；可以复用同一测试结果减少计算，但不能额外补到 K 个不同补丁。

候选筛选使用的回归/复现测试也要计费。它们只能来自 issue 与 base repo，不能查看 benchmark test_patch、隐藏测试或 gold patch。预算紧时直接采用单补丁主实验，可省去生成/筛选数十个测试的成本。

## 7. 效率与预算：报告完整账单，而不是只统计修复调用

现有 RQ4 文档针对 SWE007 报告约 142,619 token/例、365.02 s/例、36.75 成功请求/例；这是历史运行分析，本轮未重算所有原始请求。其递归汇总比请求日志高约 10%，本轮源码核对仍看到对象身份去重风险。**不能用这套历史估计证明 front_rank_v1 更便宜，也不能把成功请求口径冒充已包含所有失败计费。**

新账本每个真实请求/重试分别记录：run_id、instance_id、method、stage、逻辑 request UUID、attempt_id、provider_request_id（如有）、model、输入/输出/cache/image usage、latency、status、账单费率版本。相同物理请求的重复日志去重，不同重试不能去重；reasoning token 若已包含在 completion 中不得再次相加。

时间报告中位数、均值、P90，并分开冷启动/缓存命中、图/索引、证据处理、定位、修复、测试。嵌套阶段不可直接求和；并发 wall-clock 与逐例 latency 分开。官方 API 标价只在确实使用该接口时适用；当前私有端点没有已核实费率，保留 token 与参数化公式，不填写虚构美元。

总预算近似：

`C = Σ实例Σ方法 [C_loc + C_shared_evidence + C_context + ΣK C_patch + C_select + C_eval] + C_environment_controls + C_pilot`。

| 方案 | 主生成数 | 正式候选评测上限 | 备注 |
|---|---:|---:|---|
| 3 方法×100×K1 | 300 | 300 | 最低成本关键对照 |
| 4 方法×100×K1 | 400 | 400 | 默认推荐 |
| 5 方法×100×K1 | 500 | 500 | 加 GALA |
| 4 方法×100×K3 | 1,200 | 1,200 | 相比 K1 增加 800 次生成 |
| 4 方法×100×K10 | 4,000 | 4,000 | 不建议起步就做 |

表中没有包含定位 LLM 请求、细粒度定位、生成筛选测试和容器重复验证。100 例环境负/正控约再需 200 次评测运行；有问题的候补和重试另计。主模型选择先用开发例估算单例修复成本 p50/p90，再加约 20%–30% 的工程预留；不能据历史公开模型单价估算私有端点账单。

同时报告 `total cost / number solved`（零解决时为 undefined/∞）与解决率—成本散点/Pareto 图。Acc/Cost 可作附加指标，但不能替代解决率和成本两个原始量。单模型单配置每种方法一个点只能支持 operating-point 比较，完整曲线需额外预算配置。

节省顺序：复用相同 base_commit 镜像；复用已冻结且同配置的定位结果；共享合法原始证据缓存；独立 attempt 重置仓库；减少 candidate review 的重复全文输入；最后才减少 baseline 或样本。复用定位结果时，端到端成本仍计入其原始定位成本，同时单列本次增量花费。

## 8. 推荐论文 RQ 与正文结构

建议主张作为待检验假设：**多模态 issue 的有效定位需要把外部症状落地到仓库证据，并在预算内保留足以支持修复的代码上下文；MAGNET 通过证据理解、动态导航和流感知验证实现这一过程。** 目前只能说具备实现与部分定位证据，尚不能写成已经提高解决率或全面降低成本。

| RQ | 核心问题 | 数据/实验 | 位置 |
|---|---|---|---|
| RQ1 | 同模型下定位质量如何 | 全 92/458；File/Module/Function；Acc@1/3/5/15、Recall、MRR/MAP；明确适用分母 | 主文核心表，完整指标附录 |
| RQ2 | 收益来自哪个组件 | 去图像/网页理解、去流验证、去动态控制；同接口与预算；分别解释模态和导航收益 | 主文紧凑消融 |
| RQ3 | 固定修复器是否更易解决任务 | 同一 50+50；Applied、Resolved-single、配对胜负、区间；K3 可选 | 主文关键结果 |
| RQ4 | 开销与质量如何权衡 | 请求账本、阶段成本、预算上限、冷/热缓存、失败与长尾 | 主文一表一图，细节附录 |

多模型泛化延续现有 Qwen/Kimi/MiMo 定位实验放 RQ1 或附录；不与 RQ3 构成昂贵全因子组合。RQ2 首先选择能支撑三个贡献的最小消融，而不是对每个工程开关都写一个贡献。

Introduction 建议四段：真实多模态症状与源码之间的定位困难；现有图导航和层次定位尚未解决的证据落地问题；MAGNET 的具体策略；明确三个可检验贡献和实验范围。方法正文只保留 evidence grounding→dynamic navigation→flow-aware validation→repair-ready output 的核心链，详细打分公式和工程参数放附录。Results 按定位→机制→下游→成本推进，避免每节重复“优于 baseline”。

正文需显式保留的边界：小样本下游区间宽；现有集合曾用于开发；多语言适配并非官方原版；测试通过不等于所有视觉体验正确；近似 flow 并非动态因果证明；线上网页存在内容变化与未来修复泄漏风险。

### 案例图如何选

先记录全部四类：ours-only、baseline-only、both、neither，再从各类按预先规则选例。至少展示一个 ours-only 的证据→定位→补丁→测试链和一个 baseline-only/双方失败的边界。Chart.js legend、p5.js 渲染或 tailwindcss 样例只能作为候选，必须等真实修复评测后决定，不能复用定位命中就声称修复成功。

每个案例图包括原始截图局部、问题症状、两个方法的候选列表、两份实际补丁、同一测试输出。区分“用了同一个 API 但改错层”与“漏掉协同修改文件”，这比只展示一份绿色 diff 更能解释定位的作用。

## 9. 实施顺序与完成条件

1. **冻结输入与方法。** 核对本地 SHA，隔离 gold，去重 SWE compact 内容并追溯原始 issue；若变更输入则全部方法一致重跑，旧结果保留原条件。锁定最终 MAGNET 版本，不能继续按这 100 例修复反馈调参。
2. **开发侧跑通修复器。** 在最终名单之外选约 4–8 个覆盖语言的样本，完成补丁应用、harness、失败汇总。允许调 prompt，但不要根据最终名单结果调。
3. **环境预检与名单冻结。** 候选 50+50 的 no-op/gold controls，失败记录与同仓库候补；输出 immutable manifest。
4. **统一定位导出。** 全部 baseline 逐例 predictions、时间/token、Top-5 context；对字段白名单和 base_commit 做一致性检查。
5. **K1 主实验。** 推荐 4 方法、400 个单补丁，逐例独立目录与容器，原始日志只追加；无完整结果也保留固定分母。
6. **配对分析。** 逐集合报绝对差、wins/losses/ties、区间；定位命中/完整覆盖与修复的交叉表只作诊断，不能将不同难度子组当成因果比较。
7. **预算扩展。** 预先选择增加 GALA 或 K3；不要只给 MAGNET 多采样，也不要只重跑表现差的 baseline 直到达到预期。
8. **填充论文。** 从冻结逐例结果生成主表，保留配置来源和失败边界。已有文稿中的“应补跑失败例”须改成全方法一致的预设重试策略，而不是只为完整漂亮表格补跑。

完成条件是 100 个正式实例都有环境状态，每个方法都有一个最终补丁或明确失败，指标可由逐例记录重建，且定位/修复/评测三方的 gold 边界清楚。
