# RQ4 与 CoSIL RQ3 的下游修复对齐协议

本文说明 RQ4 如何把五种上游定位结果交给统一的下游修复器，以及当前实现与原始 CoSIL RQ3 的相同点、必要改动、候选失败含义和最终评测边界。正式参数以 `configs/protocol.json` 为准；本文解释这些参数为什么这样设置。

## 1. 实验要回答的问题

RQ4 比较的是不同定位方法给下游修复带来的效果。因此五种方法必须共享同一个修复模型、提示词、上下文构造、采样参数、候选校验、候选选择和官方评测流程。方法之间唯一允许变化的主要输入是上游给出的文件排序和函数定位结果。

这里需要区分三个结论：

1. `generated`：模型响应已经解析成非空补丁，编辑能够唯一应用，并通过当前静态检查。
2. `applied_check=true`：选中补丁能应用到目标 Git 基础提交。
3. `resolved=true`：选中补丁经过独立的官方 SWE-bench 测试并解决该样本。

前两项都不等于解决问题。报告里的 `Solved` 只来自第三项。

## 2. 完整数据流

```text
上游文件排序与函数定位
          │
          ▼
最多 Top-15 个真实候选文件
          │
          ▼
一次细粒度函数/行定位 API 调用
          │
          ▼
定位区间 ±10 行的共享修复上下文
          │
          ▼
1 个贪心候选 + 9 个随机采样候选
          │
          ▼
格式、范围、唯一匹配、非空和语法检查
          │
          ▼
按修改后内容归一化、投票、稳定破平
          │
          ▼
唯一选中补丁
          │
          ▼
一次官方 SWE-bench 评测
```

文件 Top-15 和上游函数列表会一起进入细粒度定位。细粒度定位输出 `path`、`function`、`start_line` 和 `end_line`。修复模型收到问题描述、文件列表、函数/行定位结果，以及每个定位区间前后各 10 行的源码。这样下游确实使用了文件定位和函数定位，而不是只把文件名写入日志。

## 3. 与原始 CoSIL RQ3 的逐项对比

| 环节 | 原始 CoSIL RQ3 | 当前 RQ4 | 处理理由 |
|---|---|---|---|
| 上游文件数 | Top-3 | 最多 Top-15 | 用户要求评估 Top-15 定位；不足 15 个时使用全部真实结果，不补造排名 |
| 上游函数证据 | 读取方法自己的函数定位 | 同样读取每种方法自己的函数定位 | 保留方法差异，并给后续细定位提供函数线索 |
| 细粒度定位 | 1 次，temperature=0.8，`num_samples=1` | 1 次，temperature=0.8，top_p=1 | 对齐原始随机细定位，并显式冻结 top_p |
| 细定位输出 | Agentless 文本格式后处理 | 严格 `locations` JSON，兼容单个 JSON fence | 更容易验证路径和行号，避免自由文本误解析 |
| 修复上下文 | 定位区间 ±10 行 | 定位区间 ±10 行 | 与原始 `context_window=10` 对齐 |
| 修复格式 | CoT + SEARCH/REPLACE | 英文推理 + SEARCH/REPLACE | 与 `--cot --diff_format` 的真实模板对齐 |
| 贪心候选 | 1 个，temperature=0，8192 token | 1 个，temperature=0，top_p=1，8192 token | 参数对齐并显式冻结 top_p |
| 采样候选 | 19 个，temperature=0.8，4096 token | 9 个，temperature=0.8，top_p=1，8192 token | 原脚本虽生成 20 个，但测试和 rerank 只读取 0–9；当前直接生成有效的 10 个。Qwen3.5 推理输出曾在较小预算下被截断，因此统一为 8192 |
| 候选解析 | Agentless SEARCH/REPLACE 后处理 | SEARCH/REPLACE 主格式，旧 JSON edits 兼容 | 新提示词不再要求 JSON；兼容旧完整响应便于审计历史数据 |
| 候选静态检查 | 后处理并规范化 Python 补丁 | 局部范围、唯一匹配、非空、NUL、Python AST、JSON 解析 | 在不调用官方测试的前提下拒绝明确无效补丁 |
| 候选测试 | 生成 reproduction/regression tests | 当前未启用 | 冻结数据没有跨五种方法共享且已验证的独立生成测试；不能用官方 F2P/P2P 做候选选择 |
| 候选选择 | 测试结果、去重和排序 | 有效候选按归一化内容多数票，再按改动行数和编号破平 | 确定性、可审计，并避免最终测试泄漏 |
| 最终判定 | SWE-bench harness | SWE-bench harness | 只有最终选中补丁进入正式判定 |

当前协议不是逐行复制原始脚本。它对齐了修复信息流和候选生成结构，同时保留 Top-15 研究设定、当前模型所需输出预算，以及禁止官方测试泄漏的实验约束。

## 4. 定位如何传给下游

### 4.1 文件定位

每种方法的 `normalized/<dataset>/<method>.jsonl` 包含有序 `found_files`。修复器只读取前 `file_top_k=15` 个可从 `base_commit` 解码的文本文件。路径必须是仓库内相对路径，不能包含 `..`、反斜杠或 `.git`。

### 4.2 函数定位

`found_functions` 会按文件分组。修复器在对应文件中寻找函数、类、方法或变量定义附近的源码，构造带真实行号的有界证据。函数定位为空时，程序从候选文件内可识别的定义构造有限证据；它不会伪造上游函数排名。

### 4.3 细粒度函数/行定位

细定位模型只能返回候选文件中的路径以及存在的 1-based 行区间。输出的每个区间都经过路径、类型、起止顺序和文件总行数校验。无定位、空响应和格式错误分别记录，不能直接进入修复候选生成。

### 4.4 修复上下文

同一文件内重叠或相邻的窗口会合并。最终上下文有冻结的 UTF-8 字节上限，超过上限时在任何修复候选请求前停止，防止不同方法因上下文失控而产生不可比调用。

## 5. 英文修复提示词的约束

修复模型先分析根因和预期行为，再输出一个或多个 SEARCH/REPLACE 块。提示词要求：

- 只能修改 `localized_code` 中出现的已有文件；
- SEARCH 必须逐字来自模型看到的局部源码；
- SEARCH 在完整原文件中必须唯一；
- REPLACE 保留缩进、语法、导入、类型和项目惯例；
- 允许同一补丁修改多个已定位文件；
- 无法给出可信修改时返回 `NO_VALID_EDIT`；
- 最后一个编辑块后不得继续输出说明。

这比“只输出 JSON”更接近原始 CoSIL，也避免模型把大段代码塞入 JSON 字符串时因转义错误产生 `JSONDecodeError`。解析器仍能读取旧式 `{"edits": [...]}`，但新请求以 SEARCH/REPLACE 为正式格式。

## 6. 十个候选的超参数

| 调用 | 数量 | temperature | top_p | 最大输出 token |
|---|---:|---:|---:|---:|
| 细粒度定位 | 1 | 0.8 | 1.0 | 8192 |
| 修复贪心候选 | 1 | 0 | 1.0 | 8192 |
| 修复采样候选 | 9 | 0.8 | 1.0 | 8192 |

每个方法每个样本最多 11 次收费请求。`top_p` 显式写入 API body、`attempt.json` 和候选记录。服务端是否完全支持确定性 temperature=0 取决于供应商实现，因此每次仍保存 provider request ID、usage、finish reason 和原始 response。

8192 是输出上限，不是每次必然消耗 8192 token。实际费用由 response 中的 usage 统计。当前采用 8192 是因为推理模型可能把较多 token 用于 reasoning，之前出现过 `finish_reason=length` 且正文为空；它属于模型接口兼容策略。

## 7. 候选为什么会有成功和失败

每次 API 请求本身成功，并不保证得到可用补丁。候选记录用以下状态区分：

| 状态或失败阶段 | 含义 |
|---|---|
| `generated` | 非空补丁，编辑可应用，静态检查通过；尚未执行官方测试 |
| `empty_patch` | 模型返回 `NO_VALID_EDIT`、空 edits，或应用后内容未改变 |
| `failed:response_parse` | 响应为空、被长度截断、格式不完整，或没有合法编辑块 |
| `failed:edit_application` | 文件越界、SEARCH 不在局部上下文、SEARCH 在完整文件中不唯一或不存在 |
| `failed:static_validation` | 修改为空、包含 NUL，或 Python/JSON 的确定性语法解析失败 |

因此同一组十个候选中同时存在成功和失败是正常的采样结果。temperature=0.8 会产生多样性，也会提高格式或逻辑失败概率。分析报告会汇总每种方法的候选总数、有效数、唯一补丁数和失败阶段。

## 8. 归一化、投票和破平

候选只有在 `status=generated` 且 `validation.status=passed` 时才参与选择。程序按修改后的完整文件内容建立摘要：统一换行符并忽略行尾空白，但不忽略路径、实际代码或语义内容。

选择顺序固定为：

1. 票数最多的归一化补丁组；
2. 若票数相同，选择改动行数更少的组；
3. 仍相同时，选择候选编号更小的组；
4. 组内同样按改动行数和编号选择代表补丁。

`prediction.jsonl` 保存最终候选编号、摘要、票数、改动行数、temperature、top_p 和响应格式。这样可以从最终结果追溯到具体候选和原始供应商响应。

## 9. 为什么当前没有照搬生成测试 reranker

原始 CoSIL 先生成回归测试和复现测试，再运行这些测试辅助候选排序。该步骤本身依赖额外模型调用、测试生成质量和适用于目标语言的执行环境。当前冻结输入没有一套对所有五种定位方法都相同、与候选无关且已经通过 base/gold 对照的生成测试。

官方 F2P/P2P 是最终评测证据。若先用它们挑选十个候选，再报告选中补丁的解决率，就会把测试集用于模型选择并高估结果。因此当前版本明确禁止用官方测试 rerank，只对最终选中补丁运行一次官方评测。

后续若加入生成测试 reranker，必须满足：测试在查看候选结果前按样本冻结；所有方法共享相同测试；记录生成模型、提示词、调用和源码；先验证 base/gold 行为；失败测试不能静默删除；协议名和 run-id 必须更新。

## 10. 输出文件与审计方法

每个 `attempts/<method>/<instance>/` 至少包含：

| 文件 | 内容 |
|---|---|
| `request.json` | 协议、基础提交、候选文件、上游函数和完整细定位消息 |
| `fine_localization.json` | 细定位状态、函数/行区间、usage、finish reason |
| `repair_request.json` | 十个候选共享的英文修复消息和局部源码 |
| `paid_calls/<name>/attempt.json` | 请求摘要、temperature、top_p、token 上限和 HTTP 重试记录 |
| `paid_calls/<name>/response.json` | 完整供应商响应 |
| `candidates/00.json` 至 `09.json` | 每个候选的状态、失败阶段、补丁、校验、归一化摘要和 usage |
| `prediction.jsonl` | 最终选中补丁和选择证据 |

批次级 `analysis.md` 和 `analysis.json` 汇总生成数、有效候选数、唯一补丁数、失败阶段、token 和官方解决结果。缺少官方报告时必须保持 `unknown`，不能因为补丁生成或应用成功就写成 resolved。

## 11. 正式运行要求

此次修改改变协议名、提示词、解析方式和候选选择证据，旧 run-id 不能继续复用。服务器拉取 `rq4work` 最新提交后，应先运行无收费检查，再使用新的 run-id 执行单样本；单样本的 no-op/gold 对照、十个候选和官方评测均完成后，再扩展到 50 个样本。

环境文件只决定 API 地址、密钥和模型 ID。代理直连由 `RQ4_API_DIRECT=1` 自动把 API 主机加入 `NO_PROXY`；不要把密钥写进命令、日志、Git 或本文档。
